### Minimal set for a Sandbox to actually get a backing Pod (core path, no extensions)

The core controller needs only:

1. **Namespace** `agent-sandbox-system` (created by the chart, `namespace.create: true`).
2. **ServiceAccount** `agent-sandbox-controller` in that namespace.
3. **ClusterRole** `agent-sandbox-controller` (from `templates/rbac.generated.yaml` / `k8s/rbac.generated.yaml`) granting:
   - `pods`, `services`, `persistentvolumeclaims`: create/delete/get/list/patch/update/watch
   - `events`, `events.k8s.io/events`: create/patch
   - `agents.x-k8s.io/sandboxes`: full CRUD + `sandboxes/status`, `sandboxes/finalizers` (get/patch/update)
   - `coordination.k8s.io/leases`: full (leader election)
4. **ClusterRoleBinding** `agent-sandbox-controller` (the chart bundles a single binding; no per-namespace split).
5. **Deployment** `agent-sandbox-controller` (1 replica) running the controller image. Ports 8080 (metrics), 8081 (healthz). Liveness/readiness on 8081.
6. **Service** `agent-sandbox-controller` (metrics only; optional, harmless).

**NOT required for the core path**:
- No webhooks (no ValidatingWebhook/MutatingWebhook configs in the chart or k8s/).
- No cert-manager.
- No storage class or PVCs at install time. PVCs are created per-Sandbox by the controller at runtime.
- No optional `agent-sandbox-config` ConfigMap (mounted as `optional: true` in the helm deployment; not in the raw k8s/ manifests).

Extensions (SandboxTemplate/Claim/WarmPool, group `extensions.agents.x-k8s.io`) are opt-in (`controller.extensions: true` / the `--extensions` flag) and ship with their own RBAC (`extensions-rbac.generated.yaml`). Phase 0 of coxswain only creates `agents.x-k8s.io/Sandbox`, so **core install is sufficient**; the extensions CRDs are harmless to install for completeness.

## 4. Docker + Go build feasibility

- Docker 20.10.24+dfsg1 (client + server), overlay2, Debian 12.
- Go 1.26.5 installed locally; `go.mod` requires `go 1.26.0` (module `github.com/papawattu/coxswain`).
- `Dockerfile` is a standard kubebuilder two-stage build: `ARG BASE_IMAGE=golang:1.26`, builds `cmd/main.go` into `manager`, final image `gcr.io/distroless/static:nonroot`, `USER 65532:65532`.
- `make docker-build IMG=...` will work; docker is available and new enough (20.10 supports buildkit for the two-stage build). Note: the final `gcr.io/distroless/static:nonroot` requires network access to gcr.io from the docker daemon (the homelab k3s cluster is on 192.168.1.x and the docker daemon is local, so this is fine on the devbox).

## 5. kind + k8s version envtest uses

- `kind` is not installed, so no version to report.
- `ENVTEST_K8S_VERSION` in `Makefile` is derived from the `k8s.io/api` go.mod entry, which is `v0.37.0` → envtest uses **k8s 1.37** binaries.
- A `kind` install would need a version whose kubelet is compatible with 1.37; a current `kind` release (v0.28+) tracks the latest k8s minor, so a fresh `kind` install is fine. The k3s cluster reachable from the devbox is at v1.36.2 — also fine for a quick smoke test without kind, if the goal is just "apply a Loop, see the controller log it."

## Recommended minimal e2e sequence (using the existing k3s cluster — fastest, no new tooling)

```sh
# 1. Build the operator image (also validates the Dockerfile)
cd /home/jamie/projects/coxswain
make docker-build IMG=example.com/coxscaf:v0.0.1

# 2. Push to a registry the k3s cluster can pull from, or
#    for a local-only smoke test: `docker save` + load on the k3s nodes.
#    (Alternatively, if you go the kind route, skip this and use `kind load` below.)

# 3. Install agent-sandbox core (CRDs + controller) — core only, no extensions
A=/home/jamie/go/pkg/mod/sigs.k8s.io/agent-sandbox@v1.0.4/k8s
kubectl apply -f $A/crds/agents.x-k8s.io_sandboxes.yaml
# Patch the ko:// placeholder in controller.yaml to the real image before applying:
sed -i.bak 's|ko://sigs.k8s.io/agent-sandbox/cmd/agent-sandbox-controller|registry.k8s.io/agent-sandbox/agent-sandbox-controller:TAG|' $A/controller.yaml
kubectl apply -f $A/rbac.generated.yaml
kubectl apply -f $A/controller.yaml
kubectl get pods -n agent-sandbox-system   # wait for Ready

# 4. Install coxswain
make install
make deploy IMG=example.com/coxscaf:v0.0.1
kubectl get pods -n coxscaf-system

# 5. Apply a Loop (the existing sample has an empty spec; use a real one)
cat > /tmp/loop.yaml <<'EOF'
apiVersion: cox.cox.dev/v1alpha1
kind: Loop
metadata:
  name: phase0-smoke
  namespace: coxscaf-system
spec:
  goal: "smoke test"
  workspace:
    repo: "https://github.com/papawattu/pixme.git"
EOF
kubectl apply -f /tmp/loop.yaml

# 6. Verify
kubectl get loops -n coxscaf-system -o wide
kubectl get sandboxes -n coxscaf-system
kubectl logs -n coxscaf-system -l control-plane=controller-manager | grep -i 'sandbox'
```

## Key caveats

- The repo's **existing e2e suite** (`test/e2e/e2e_suite_test.go`) already assumes a kind cluster named `kind` (overridable via `KIND_CLUSTER` env), installs CertManager by default (skippable with `CERT_MANAGER_INSTALL_SKIP=true` — coxswain has no webhooks, so this can be skipped), and runs the metrics-curl pod. It does NOT install agent-sandbox; that step must be added or run manually before `make test` reaches the Loop-apply assertion.
- `config/samples/cox_v1alpha1_loop.yaml` has an **empty spec** (the scaffold default). It will fail validation as-is (Loop requires `goal` and `workspace.repo`). Replace with a real Loop before applying.
- The coxswain `LoopReconciler` (Phase 0) creates a Sandbox with a single `agent` container running `sh -c "sleep infinity"` and image `SandboxImage` (overridable, defaults to a Go dev image). For the smoke test this is fine; for Phase 1 the runner image would replace it.
- No cert-manager is needed for coxswain itself (no webhooks in the scaffold). The agent-sandbox controller also does not need cert-manager.
